# Operation r600: 0x70 subtype 1 — partial, VM-backed path

## Status

This case is **not fully decoded**. It is retained because it exposed an alternate send path and motivated reusable stack-attribution improvements. No semantic name is assigned to subtype 1.

Historical operation **r600**, monitor operation **1962**, contains a complete 52-byte socket send with a 48-byte plaintext message. It was attributed to `MapleStory.exe` on `172.16.1.203:54118 -> 44.234.174.136:8579`.

Historical evidence: [r600.json](../../../evidence/outgoing/20261114T210123Z-r600.json)

## Historical byte structure

The original plaintext is:

```text
70 00 01 64 00 00 00 44 35 e3 cb 44 35 e3 cb 02 00 00 00 00
5d 45 d1 1b 16 f5 70 a4 fe 18 0d 66 70 de 86 69 d3 c5 a4 94
f0 4f ff ff 00 00 00 00
```

Across six historical observations:

| Offset range | Structural observation | Meaning |
|---|---|---|
| `0..1` | `0x70` | Opcode |
| `2` | `1` | Subtype |
| `3..6` | Constant 100 | Unknown numeric field |
| `7..10` | One varying 32-bit value | Unknown |
| `11..14` | Exact repeat of the value at `7..10` | Unknown repeated field |
| `15..18` | Constant 2 | Unknown numeric field |
| `19` | Constant 0 | Unknown byte/field boundary |
| `20..39` | 20 varying bytes | Unknown; not automatically a hash, token, or identifier |
| `40..47` | Same final eight bytes in these six observations | Later observations contain zeros, so this is state-dependent, not a universal constant |

These comparisons reveal repetition and variation, not semantic fields. No decoder names were invented from them.

## Constructor/send-path findings

Two dynamic constructor candidates found during static analysis serialized only 23 bytes, so they cannot explain this 48-byte message. They were rejected by layout rather than timing.

A fresh trace captured other `0x70` subtypes while subtype 1 appeared on the wire, but subtype 1 had no canonical SendPacket trace. This is evidence of an alternate path, not proof that the message was absent or that its constructor was unused.

An address-enabled monitor capture then recorded subtype-1 operation **r14756** with return addresses including:

- `0x141667021` — MapleStory RVA `0x1667021`, immediately after an indirect four-argument socket call at RVA `0x166701b`;
- `0x141666f40` — MapleStory RVA `0x1666f40`, the send-wrapper entry, but this may be a scan-only/stale stack value and is not called a proven caller;
- `0x144c0aa61` — runtime-generated code without a disk-function mapping.

The indirect call's live target resolved into Wine's `ws2_32.dll` at offset `0x10ea0`. The wrapper has a direct caller at RVA `0x2d4e8f7` in a larger dispatch path. This supports lower-level forwarding of an already prepared buffer after VM-backed activity.

The current evidence does **not** reveal where the 20 variable bytes are generated or what they mean. A search of recent writable process memory found no retained plaintext buffer suitable for a targeted field watch.

## Tracer limitations preserved

The fresh deep trace included two `invalid_intermediate_length` events and later writes unrelated to the original constructor. Those watches can become stale when an object is not sent immediately or its stack address is reused. The large later snapshots were not used as subtype-1 evidence.

Only complete send bodies, direct caller evidence, and explicit socket/packet observations were used. No field layout was inferred from the invalid snapshots.

## Reusable improvements from this case

### Exact stack addresses

The monitor previously discarded its recovered addresses after module resolution. It now writes `stack_addresses` in stack order, including unresolved and scan-only entries. `traffic-ledger.py` retains them in socket operations and reports address-to-image range matches with image-load evidence.

An image-range match is not instruction-level proof. Scanned frames can be stale, and ambiguous ranges remain marked ambiguous.

### Native image grouping

The maps parser grouped all mappings of one native path into a single range. Distant repeated loads therefore created false ambiguity. It now starts a new native image at every offset-zero mapping, with a regression test covering two distant loads of the same file.

Existing captures cannot be retroactively corrected. Their ambiguity remains evidence of the old data model; a fresh corrected capture is required.
