# Filtering the r374 update-rate report

## Question and result

Can the client suppress every message with the **r374 form**—MapleStory `0x70`, subtype 5—without affecting other traffic?

The policy and suppression mechanism worked in a controlled live experiment. Exactly **one** update-rate report was dropped before transmission. The other **232 traced sends** were allowed, other `0x70` subtype-1 messages remained visible on the wire, and the client stayed connected during the filtered observation window.

This is **not yet evidence that the report is noncritical or safe to block indefinitely**. Only one target occurrence was tested, for a short period. Server-side necessity and delayed effects remain unknown.

## Live procedure

```bash
  --attach --log-dir /home/bob/Downloads/client-control/captures
```

The existing SendPacket observer applied the exact field policy. The trace-only driver was used because the experiment did not need another `tcpdump` instance:


The policy can alternatively be used through `capture-outgoing.sh --policy ...`. The ordinary wrapper also captures packets with `tcpdump`; its prerequisites and cleanup behavior apply.

## Exact dropped message

The dropped message was ledger **r6967**, trace event **6807**, construction ID `f9a60a76204f49868042f20e50788390:6644`.

```text
70 00 | 05 | 42 20 c7 09 | e2 1e 00 00
```

| Field | Value |
|---|---:|
| Opcode | `0x70` |
| Subtype | `5` |
| Tick | `164044866` ms |
| Update count | `7906` main-loop iterations |

Its constructor caller was RVA `0xd049a2`; its SendPacket caller was RVA `0xd049f3`. The decision was `drop`, `forward: false`, with the expected policy hash and rule ID. `constructor_missing` was false.

The observer redirected SendPacket to return success to its caller without executing the normal downstream transmission. This is an intentional modification of control flow at the send boundary, not a network black hole.

## Observed result

- **233** traced client sends occurred.
- **One** was dropped; **all 232 others** were allowed.
- There were zero send errors, deep-trace gaps, or observer cleanup errors.
- The counter/report caller's normal post-send path still runs, so suppression also resets the update counter.
- No socket or reconstructed-packet message with the dropped plaintext was observed.
- Other `0x70` subtype-1 messages were observed on the wire during the filter window: 18 records across socket and packet observation layers. These are evidence that the rule did not suppress the entire `0x70` family.
- The combined ledger's strict observed-byte check passed with 14,580 raw hashes verified and no reported problems. This does not prove absolute sensor coverage.
- The original game connection remained established for **96.47 seconds after the drop while the filter was active**, and the independent monitor continued for **118.21 seconds after the drop**.

At a later health check, the original port-8548 connection was absent, but the MapleStory process and MapleMarket scanner were still running and an established game connection existed on port 8562. The endpoint change is recorded without claiming that filtering caused it or that channel switching excludes every malfunction.

## What is not proven

- Only one subtype-5 occurrence was dropped. The policy covers subsequent matching reports, but this run did not test multiple drops.
- The short observation window does not exclude delayed disconnects, anti-cheat responses, missing diagnostics, or other server-side effects.
- No experiment established that the message is unnecessary for login, channel changes, liveness, or a particular game phase.
- No server response or server-side importance can be inferred from the successful client send suppression alone.
- The filter was removed after the experiment. Normal message construction/transmission resumed when the observer detached.

A longer audit should suppress multiple reports across gameplay phases and compare connection health, scanner progress, and server behavior before this message is called noncritical.
