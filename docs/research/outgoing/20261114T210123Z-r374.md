# Outgoing socket operation r374: evidence-led reverse engineering

## Conclusion

Ledger **r374**, monitor **operation 478**, is a MapleStory **client update-rate/performance report**.

Its complete decrypted application body contains:

- opcode `0x70`, subtype `5`;
- a 32-bit millisecond tick: **`158487426`**;
- a 32-bit main-loop update count: **`3984`**, accumulated since the previous report.

The construction path reads the count, sends it, and then resets it to zero. The counter is incremented once per main update-loop iteration. There are no shop, trade, movement, combat, or other gameplay fields in this 11-byte body.

This establishes the message's functional content. It does not establish the server-side use of the report or the exact higher-level scheduling trigger. A later equivalent message runtime-confirmed the constructor and SendPacket path, and a one-shot execution watch captured the report's immediate caller in runtime-generated code. Historical r374 itself was not ptrace-traced, so that distinction remains explicit below.

## Evidence labels

- **Historical observed:** directly present in r374's monitor or packet records.
- **Historical derived:** calculated from those bytes with the recorded framing/decryption procedure.
- **Runtime corroboration:** observed for a later equivalent message or current object, not for historical r374.
- **Static:** present in the fingerprinted executable; not alone proof of a runtime call.
- **Unknown:** evidence is absent or ambiguous; no name or cause is guessed.

## 3. Exact bytes and transport decode

Historical socket payload:

```text
92 ae 99 ae | f4 97 eb fa 2d 30 1f 01 42 8f 7d
```

Raw SHA-256:

```text
57e167ff91ee767a25baf8763656d5d433ad2d22127bce5fe2138402b6b2f6fd
```

The four-byte MapleStory header contains two little-endian words:

```text
word0 = 0xae92
word1 = 0xae99
word0 XOR word1 = 11
```

The declaration equals the captured body length: `15 - 4 = 11`.

Two consecutive stream headers derived a unique starting IV, `b1398800`. Rolling to this frame gives IV `04e44dae`, with a passing synchronization check. The recorded transport interpretation is AES-256-OFB, start layer 0.

Historical derived plaintext:

```text
70 00 | 05 | 82 53 72 09 | 90 0f 00 00
```

Plaintext SHA-256:

```text
d0e70156af56d4682d2dbb2db1adb3a88a1d8c4b413bc215f93416248026f470
```

| Offset | Bytes | Current bounded decode |
|---|---|---|
| `0x00` | `70 00` | opcode `0x0070` |
| `0x02` | `05` | subtype `5` |
| `0x03` | `82 53 72 09` | little-endian tick `0x09725382` = **`158487426` ms** |
| `0x07` | `90 0f 00 00` | little-endian count `0x00000f90` = **`3984` updates** |

No trailing bytes remain. The original ledger's decode remains unchanged inside `decode`; the exporter's `current_field_decode` records the newer `update_rate_report` interpretation separately.

The automatic cipher metadata retains `start_layer_evidence: opcode_range_heuristic`. The known `0x70` frame and other structured frames support the interpretation, but the historical plaintext is still transport-derived, not a historical `COutPacket` capture.

## 5. Constructor and serialization path

The matching function is **RVA `0xd04970`..`0xd04a33`**:

```text
0xd04993  mov edx, 0x70
0xd04998  lea rcx, [rsp + 0x30]
0xd0499d  call COutPacket constructor, RVA 0x7614b0

0xd049a3  mov dl, 5
0xd049aa  call Encode1, RVA 0x7617d0

0xd049af  call RVA 0x2a9ec10
0xd049b4  mov edx, eax
0xd049bb  call Encode4, RVA 0x761960

0xd049c0  call RVA 0xd1f3c0
0xd049cf  mov rax, [rax]
0xd049d7  call [rax + 0xf0]
0xd049dd  mov edx, eax
0xd049e4  call Encode4, RVA 0x761960

0xd049e9  lea rcx, [rsp + 0x30]
0xd049ee  call SendPacket, RVA 0x1661780

0xd049f3  call RVA 0xd1f3c0
0xd04a0a  call [rax + 0x100]
0xd04a16  call COutPacket destructor, RVA 0x7615a0
```

The function allocates a `0x498`-byte stack frame and places the packet object at `rsp+0x30`. Its incoming RCX/RDX values are saved but not read by the exported body; both fields come from global/object state.

### Runtime confirmation of this path

A later equivalent message had construction ID `a37730be8ac3470b9cd5bb3793f8334a:427` and plaintext:

```text
70 00 | 05 | 14 58 ae 09 | 97 14 00 00
```

That is tick `162420756` and update count `5271`. Its read-only trace shows:

- constructor caller RVA `0xd049a2`, immediately after the candidate's constructor call;
- five field changes: initialization length 0, opcode length 2, subtype length 3, tick length 7, count length 11;
- SendPacket caller RVA `0xd049f3`, immediately after the candidate's SendPacket call;
- `constructor_missing: false`, `dropped: false`;
- zero send errors, deep gaps, or drops, and successful restoration/detach.

This runtime-confirms the path for the equivalent message. It does not manufacture a historical runtime trace for r374.

## 6. First field: millisecond tick

RVA `0x2a9ec10` loads the global object pointer at `0x143bf38c8` and jumps to RVA `0x2d0a180`:

```asm
mov eax, dword ptr [rcx + 0x60]
ret
```

That object field supplies the first `Encode4` input. Current read-only samples in `r374-timer-samples.json` show values `163350156`, `163350246`, `163350336`, `163350456`, and `163350546` over approximately 500 ms. This supports a cached millisecond tick with update jitter.

The absolute epoch of this tick is not established, so `158487426` must not be presented as a Unix timestamp or wall-clock time. Historical r374 did not include a direct EAX or timer-object snapshot.

## 7. Second field: main-loop update counter

RVA `0xd1f3c0` returns the global object pointer at `0x143bda7b0`. Runtime resolution identified the relevant virtual table at `0x1435a51b0` and three consecutive methods:

| Vtable offset | Method RVA | Behavior |
|---|---|---|
| `0xf0` | `0x2dae6e0` | `mov eax, [rcx + 0x30e0]; ret` — read count |
| `0xf8` | `0x2dae6f0` | `inc dword ptr [rcx + 0x30e0]; ret` — increment count |
| `0x100` | `0x2dae700` | `mov dword ptr [rcx + 0x30e0], 0; ret` — reset count |

A one-second four-byte write watch recorded **35 writes**, all at RVA `0x2dae6f6`, immediately after the increment instruction. Values increased from 1650 to 1684 in that sample. The writer's stack identified return RVA `0x2da1ed0`.

The containing main update-loop code does this after a series of subsystem updates:

```asm
; rsi is the counter object in the observed writer path
mov rax, [rsi]
mov rcx, rsi
call qword ptr [rax + 0xf8]    ; increment object+0x30e0
; 0x2da1ed0 is the return address seen by the watch
```

Therefore the field counts main-loop update iterations. It is not a shop count, packet count, price, item ID, or other gameplay value.

A generic protected-integer setter at RVA `0x90d710` can write the same field with seed/rotation/checksum logic. The actual captured increment path was instead the direct `inc` above. The raw `3984` must not be decoded using that unrelated setter without evidence that it applies to the historical state.

After SendPacket, the report function calls vtable offset `0x100`, now resolved to the reset method. Thus the next report's count starts from zero. This read/increment/reset triad supports the **update-rate/performance report** interpretation: successive tick/count pairs can describe update rate. Actual server-side use remains unobserved.

## 8. Immediate caller and scheduling evidence

Static scans found no direct caller or static 64-bit pointer to RVA `0xd04970` in the disk image. No writable runtime pointer or direct branch to it was found in the live mapped image either.

A focused execution watch at `0x140d04970` then captured the next report with:

- RIP/RVA: `0x140d04970` / `0xd04970`;
- stack pointer: `0x10e648`;
- first stack word: `0x144a77392`;
- immediate caller return RVA: **`0x4a77392`**;
- clean debug-register restoration and no client-memory writes.

That caller has no containing disk `.pdata` function and no corresponding mapped raw executable bytes in the disk image. It is runtime-generated/virtualized code, consistent with this build's protected paths. The immediate caller is known, but the higher-level original scheduler remains unidentified.

The later equivalent packet observation had **no incoming message on the same connection within one second** before the report. This is evidence against calling it an immediate response to the historical incoming `0x72`. It does not prove a universal period or exclude all server-triggered scheduling.

## 9. Remaining limits

- Historical r374 was not ptrace-traced; its original constructor registers, original buffers, iovec contents, and runtime module caller were not captured.
- The later equivalent trace proves the same static construction path for a new message, not the historical event retroactively.
- The immediate historical socket caller is the MapleStory process; the higher-level GRAP-versus-game scheduler is not established.
- The tick's epoch and the exact higher-level report scheduler/period are unknown.
- The server-side use of the tick/count pair and any application response are unobserved; no causation is inferred from timing.
- Raw hashes prove stored-byte integrity, not absolute sensor coverage, server receipt, or semantic completeness of unrelated messages.

## 10. Scoped filtering experiment

The exact subtype-5 form was subsequently filtered with [analysis/policies/drop-update-rate-report.json](../../../analysis/policies/drop-update-rate-report.json). One update-rate report was dropped before transmission, 232 other traced sends were allowed, other `0x70` subtype-1 traffic remained on the wire, and the original game connection stayed established for 96.47 seconds while filtering continued after the drop.

This was a successful short suppression experiment, not proof that the report is noncritical or safe to block permanently. The filter was removed after the experiment.
