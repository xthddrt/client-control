# Focused 0x32b and pickup capture

Use this module for a controlled sequence of one mob kill followed by pickup of all drops from that mob. Do not kill another mob before collecting the previous drop.

## Run

```bash
tools-QUARANTINE/capture-32b.sh 180
```

The wrapper requests sudo authentication, auto-detects the game PID and current remote ports, and records for the selected duration. It does not track combat RNG or general attack state.

## What is recorded

Only opcodes `0x32b`, `0x407`, and `0x13b` receive focused event records. Each record includes:

- timestamp, opcode, length, and complete body;
- caller RVA and eight return-stack entries for construction analysis;
- packet and body addresses;
- before/after bytes for every changed 1 MiB writable-memory chunk;
- full-duplex pcap of the current game endpoints;
- timestamped offline-decrypted frames when IV recovery succeeds.

The observer takes one full-memory baseline before any kill and another snapshot after each focused packet. This limits performance impact while preserving all memory changes between focused events.

## Output

- `32b-events-*.jsonl` — focused packets, caller data, and full-memory diffs.
- `32b-session-*.pcap` — all client/server traffic on the current endpoints.
- `32b-session-*.pcap.decrypted.json` — timestamped decrypted frames.
- `32b-driver-*.log` and `32b-decode-*.log` — capture and decryption diagnostics.

Captures may contain private traffic, tokens, and memory. They are normally mode `0600` and must not be committed.

## Analysis targets

The `0x14–0x16` and `0x20–0x23` fields should be compared against the next inbound drop/spawn and pickup response, not assumed to be item IDs or quantities. If they are metadata, altering them should not change the actual reward. If the server uses them as reward inputs, a controlled single-field edit with exact readback and restoration will show the difference.

Full-memory snapshots are not atomic across all game threads, so concurrent changes remain possible. No game memory or packets are modified by this module.

## Controlled field override

For per-field pickup experiments without full-memory snapshots, prefer `TEST_MODE=2` through `TEST_MODE=11` with `tools-QUARANTINE/capture-packets.sh 90`. These modes keep the drop object ID at `0x0f` unchanged, capture a native pickup, increment one selected field on a later pickup, restore it after sending, and record the resulting `0x8b` credit. `TEST_MODE=1` instead doubles the meso amount in the incoming `0x471` spawn. See `PACKETS.md` for the mode map and guarded-restoration behavior.

After collecting a native baseline, the older override observer can also test one explicit field:

```bash
ALTER_32B=1 ALTER_OFFSET=0x14 ALTER_SIZE=3 ALTER_VALUE=0 tools-QUARANTINE/capture-32b.sh 120
```

For the final four-byte field instead:

```bash
ALTER_32B=1 ALTER_OFFSET=0x20 ALTER_SIZE=4 ALTER_VALUE=0 tools-QUARANTINE/capture-32b.sh 120
```

The first `0x32b` is recorded unchanged. The second is modified with exact readback, and the original field bytes are restored immediately after `SendPacket` returns. The experiment records native and override packets, restoration status, and full-duplex server traffic. A changed drop would show that the server uses the edited metadata; an unchanged drop is consistent with `0x32b` being a report rather than an RNG input. Repeated or invalid values may trigger server-side validation or disconnects.
